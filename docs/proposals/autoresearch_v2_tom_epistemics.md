## 1. Purpose and Scope

This document provides a detailed technical specification for two of AutoResearch v2's most distinctive subsystems:

1. **Theory-of-Mind (ToM) Layer:** A set of mechanisms that model the mental states (beliefs, priors, standards, biases) of scientific reviewers and human collaborators, using those models to drive research strategy and manuscript revision.

2. **Zero-Trust Epistemic Verification Stack:** A multi-gate system that independently verifies every significant claim generated by the research system before it appears in any output, using diverse verification methods to avoid single-model blind spots.

These two subsystems are deliberately addressed together because they are deeply coupled: the epistemic verification stack determines *what is true*, while the ToM layer determines *what is believable and communicable* — and any system that optimizes for the latter without grounding in the former risks becoming manipulative rather than scientific.

---

## 2. Why ToM Matters for Autonomous Science

### 2.1 Science as Social Epistemology

Science is not merely the production of correct facts. It is a social process by which a community of minds, with heterogeneous priors and standards, comes to a shared (and revisable) understanding of the world. A scientific result is only meaningful when it has been communicated, evaluated, and incorporated into the community's knowledge base.

Current AI scientist systems treat science as a **solo production task**: generate a hypothesis, test it, write it up, score it. This misses the fundamental social dimension. Consider:

- A mathematically correct result written in notation opaque to the target community will not be read.
- A result that contradicts a community's strong prior without carefully addressing that prior will be rejected — even if correct.
- A result produced by a method that a domain community has principled objections to will not be accepted regardless of its statistical significance.

ToM is the capability that allows an AI system to model these dynamics and produce research outputs that are not just correct, but *persuasive in the right way* — building compelling evidential cases for minds with specific epistemic starting points.

### 2.2 The Failure Mode of Homogeneous Review

If an AI system uses a single model (or architecturally similar models) for both generation and review, it inherits a shared set of systematic biases. The reviewing model will tend to find plausible the same things the generating model finds plausible, creating an epistemic echo chamber.

This is not merely a theoretical concern. Empirical studies on LLM self-evaluation `[to verify: cite relevant 2024–2025 papers on LLM self-evaluation biases]` have found that models are significantly better at evaluating outputs from other models or humans than at detecting flaws in their own outputs.

The solution is **epistemic diversity**: using structurally different evaluation perspectives (different model architectures, different prompt priors, different optimization targets) to stress-test generated content.

### 2.3 ToM Levels Required for Scientific Review

Human ToM research identifies multiple "orders" of belief representation:

- **1st order:** "I believe X is true."
- **2nd order:** "I believe the reviewer believes X is insufficient evidence."
- **3rd order:** "I believe the reviewer believes that the field expects X level of evidence."

Effective scientific communication requires at least **2nd-order ToM** (modeling what reviewers believe) and ideally **3rd-order** (modeling what reviewers believe the community expects). HRDE's ToM implementation targets 2nd-order as MVP, with 3rd-order as a post-MVP upgrade.

## 3. ToM Architecture: The Socio-Cognitive Layer

### 3.1 Component Overview

The Socio-Cognitive Layer consists of four interacting components:

### 3.2 Belief State Tracker

The Belief State Tracker maintains a probabilistic model of relevant stakeholder beliefs:

```python
@dataclass
class BeliefState:
    stakeholder_id: str       # e.g., "skeptic_reviewer", "human_collaborator_1"
    stakeholder_type: Literal["reviewer_persona", "human_collaborator", "domain_community"]

    # Beliefs about the research topic
    prior_confidence: float   # 0=no prior, 1=very strong prior belief in topic
    evidence_threshold: str   # "anecdotal", "pilot", "large_n", "replication"
    preferred_method: list[str]  # Preferred methodological approaches
    known_objections: list[str]  # Known objections this stakeholder archetype raises

    # Beliefs about the system's current output
    current_confidence: float  # Updated during dialogue rounds
    unresolved_concerns: list[str]

    # Metadata
    last_updated: datetime
    confidence_in_model: float  # How confident the system is in this belief model
```

**How beliefs are inferred:**
- Reviewer personas: initialized from literature on reviewer behavior, NeurIPS/ICLR meta-reviews `[to verify: cite relevant reviewer behavior studies]`, and curated few-shot examples
- Human collaborators: inferred from the initial research directive, preference questions at run start, and updates based on feedback during HITL intervention points

### 3.3 Intent Alignment Planner

The Intent Alignment Planner translates the CIM and Belief State Tracker outputs into **DOG objective priorities**:

- If the CIM shows high novelty appetite + low rigor requirement → increase budget for hypothesis generation, reduce budget for literature exhaustiveness
- If the Belief State Tracker indicates the target venue (e.g., "Nature Methods") has strong reproducibility standards → increase priority of reproducibility objectives
- If the domain expert reviewer has high confidence in an alternative theory → prioritize objectives that address that alternative

**Critical constraint:** The Planner may only adjust *presentation strategy and objective priorities*. It may not modify, suppress, or reframe empirical findings that have passed the epistemic verification stack.

### 3.4 Interpretability Diplomat

The Interpretability Diplomat handles the final stage of manuscript preparation: ensuring that verified claims are communicated in a way that is accessible to different cognitive audiences.

**What it does:**
- Rewrites technical sections for different expertise levels (e.g., a "plain language summary" alongside the technical contribution)
- Adjusts framing to address known reviewer concerns identified by the Belief State Tracker
- Ensures that the abstract and introduction build the reader's prior toward accepting the main result before presenting it

**What it does NOT do:**
- It does not remove, soften, or reframe negative results
- It does not change numerical values, statistical interpretations, or methodological descriptions
- It does not omit limitations identified by the reviewer council

## 4. Reviewer Council: Personas, Rubrics, and Dialogue Protocol

### 4.1 The Five Reviewer Personas

Each persona is defined by: (a) a system prompt that establishes their epistemic stance and review style, (b) a set of weighted evaluation dimensions, and (c) a library of archetypal objections.

#### Persona 1: The Skeptic

**Core stance:** "I will accept this paper only if the evidence is overwhelming and the methodology is airtight."

**Priority dimensions:**
- Statistical rigor (weight: 0.35)
- Effect size and practical significance (weight: 0.25)
- Methodology transparency (weight: 0.20)
- Absence of overclaiming (weight: 0.20)

**Archetypal objections:**
- "The confidence intervals are too wide to support this conclusion."
- "The comparison baseline is not appropriately chosen."
- "The authors conflate statistical significance with practical significance."
- "N is too small; this could be a false positive."

**Acceptance threshold:** This persona has the highest bar. Acceptance signals from The Skeptic carry the most weight in the final council verdict.

---

#### Persona 2: The Engineer

**Core stance:** "A result is only useful if someone else can reproduce it."

**Priority dimensions:**
- Code availability and quality (weight: 0.30)
- Reproducibility of results (weight: 0.30)
- Computational efficiency and resource reporting (weight: 0.20)
- Ablation completeness (weight: 0.20)

**Archetypal objections:**
- "The code is not available / not runnable."
- "The hyperparameter search space is not described."
- "Runtime and compute costs are not reported."
- "Key ablation experiments are missing."

---

#### Persona 3: The Visionary

**Core stance:** "This needs to matter. What does this change about how we think?"

**Priority dimensions:**
- Novelty of contribution (weight: 0.40)
- Breadth of impact (weight: 0.30)
- Quality of motivation and framing (weight: 0.30)

**Archetypal objections:**
- "This is incremental. How is this different from [existing paper]?"
- "The authors bury the lead — the most interesting finding is not emphasized."
- "The broader impact section is boilerplate."

---

#### Persona 4: The Domain Expert

**Core stance:** "I know this field. I will catch anything that doesn't fit the domain's knowledge and norms."

**Priority dimensions:**
- Coverage of relevant prior work (weight: 0.35)
- Domain-specific correctness (weight: 0.35)
- Appropriate use of domain methodology (weight: 0.30)

**Archetypal objections:**
- "The authors missed [key paper] which contradicts their main claim."
- "This violates a known constraint in [domain]."
- "The evaluation metric chosen is not standard in this field."

> **Implementation note:** The Domain Expert persona must be seeded with domain-specific knowledge at run time (retrieved from the literature search phase). A single generic Domain Expert prompt is insufficient; the system must parameterize this persona with the specific domain of the research run.

---

#### Persona 5: The Ethicist

**Core stance:** "Research has consequences. I'm responsible for making sure this doesn't cause harm."

**Priority dimensions:**
- Dual-use risk assessment (weight: 0.30)
- Dataset and demographic bias (weight: 0.30)
- Environmental / compute cost (weight: 0.20)
- Societal impact framing (weight: 0.20)

**Archetypal objections:**
- "The training data may contain bias not addressed in the limitations."
- "The potential for misuse is not discussed."
- "The compute cost is disproportionate to the claimed contribution."

---

### 4.2 The 7-Dimension Scoring Rubric

All five personas score the manuscript on a common 7-point rubric (1–7 scale, where 4 = borderline, 6+ = strong accept):

| Dimension | Description |
|---|---|
| **Novelty** | How different is this from the existing literature? |
| **Rigor** | How sound are the methods and statistical treatment? |
| **Clarity** | How well does the writing communicate the contribution? |
| **Significance** | How important is this for the field or for science broadly? |
| **Reproducibility** | Could another team reproduce this result independently? |
| **Ethics** | Are risks, biases, and limitations adequately addressed? |
| **Related Work** | Is the prior literature covered with appropriate depth? |

Each persona applies different weights to these dimensions when computing their overall score. The final acceptance decision uses a **weighted consensus** across the council.

### 4.3 Adversarial Dialogue Protocol

```
┌─────────────────────────────────────────────────────┐
│  ROUND 1: BLIND REVIEW                               │
│  Each reviewer independently scores manuscript       │
│  No inter-reviewer communication                     │

                        │
                        ▼
┌─────────────────────────────────────────────────────┐
│  AUTHOR AGENT RECEIVES ALL REVIEWS                   │

└───────────────────────┬─────────────────────────────┘
                        │
                        ▼
┌─────────────────────────────────────────────────────┐

│  Each reviewer reads rebuttal + updates score        │
│  Reviewer may request additional clarification       │
└───────────────────────┬─────────────────────────────┘
                        │
                        ▼
┌─────────────────────────────────────────────────────┐
│  AUTHOR AGENT REVISION                               │
│  Manuscript is revised based on Round 2 feedback     │
│  (All changes logged in audit trail)                 │
└───────────────────────┬─────────────────────────────┘
                        │
                        ▼
┌─────────────────────────────────────────────────────┐
│  ROUND 3: FINAL ASSESSMENT                           │
│  Reviewers give final scores                         │
│  Council decision computed (weighted consensus)      │
└───────────────────────┬─────────────────────────────┘
                        │
               ┌────────┴────────┐
               ▼                 ▼
        [ACCEPT]           [REVISE & RESUBMIT]
                                 │
                                 ▼
                     [Back to Discovery Forest
                      for targeted revision]
```

**Council decision rule (configurable):**
- Default: ≥ 4 of 5 reviewers score ≥ 4.5 → Accept
- Stringent mode: Mean score ≥ 5.0 AND no reviewer scores below 3.0 → Accept
- Fast mode: ≥ 3 of 5 reviewers score ≥ 4.0 → Accept (for rapid-iteration runs)

**After 3 rounds without consensus:** The manuscript enters a "structured revision" phase where the specific failing dimension (e.g., "The Skeptic's rigor score is consistently below 3.0") is surfaced to the Hyper-Kernel as a targeted improvement task.

### 4.4 Rebuttal Constraints

The Author Agent's rebuttal is subject to strict constraints enforced by the Epistemic Verification Stack:

1. **No new experimental claims:** The rebuttal cannot introduce new experimental results.
2. **Evidence-grounded:** Every claim in the rebuttal must cite either an execution log entry, an arXiv paper (verified DOI), or an explicit logical inference.
3. **Acknowledge unresolvable concerns:** If a reviewer's concern is valid but cannot be addressed within the current run (e.g., requires a new experiment), the rebuttal must acknowledge this and propose it as future work.
4. **No rhetorical substitution:** The rebuttal may not substitute rhetorical argumentation for empirical evidence.

## 5. Collaborator Intent Modeling

### 5.1 Intent Dimensions

The Collaborator Intent Model (CIM) captures the following dimensions from the human collaborator's perspective:

| Dimension | Scale | Description |
|---|---|---|
| **Risk appetite** | 0–1 | 0 = safe/incremental, 1 = high-risk/novel |
| **Rigor vs. speed** | 0–1 | 0 = speed-first, 1 = rigor-first |
| **Interpretability priority** | 0–1 | How much to explain the system's reasoning in outputs |
| **Venue target** | Categorical | e.g., "NeurIPS", "Nature", "arXiv preprint", "internal" |
| **Domain expertise level** | 0–1 | 0 = novice, 1 = world expert |
| **Collaboration style** | Categorical | "gate-only", "step-by-step", "fully-autonomous" |

### 5.2 Intent Inference

Intent is inferred from multiple signals:

**Signal 1: Initial directive parsing**
The research directive is parsed by an intent extraction LLM call that maps key phrases to CIM dimensions:
- "quick exploration" → speed bias
- "publication-ready" + target venue → rigor + venue target
- "we want to understand why" → interpretability priority
- "unconventional approach" → risk appetite

**Signal 2: HITL intervention feedback**
When the human collaborator intervenes at a SmartPause point (a point where the system surfaces its current direction and asks for confirmation), their response is used to update the CIM:
- Approval → reinforce current direction
- Redirect → update relevant dimension in CIM

**Signal 3: Feedback on intermediate outputs**
If the collaborator reviews a draft and comments "this needs more evidence," that updates the rigor dimension.

### 5.3 CIM in the Compute Planner

The CIM directly influences compute budget allocation:

```python
def adjust_budget_for_intent(base_budget: dict, cim: CollaboratorIntentModel) -> dict:
    """
    Adjust objective budgets based on collaborator intent.
    base_budget: {objective_type: float} normalized to sum to 1.0
    """
    adjusted = base_budget.copy()

    # High rigor → more budget for verification and review
    adjusted["verification"] *= (1 + 0.5 * cim.rigor_vs_speed)
    adjusted["review"] *= (1 + 0.3 * cim.rigor_vs_speed)

    # High risk appetite → more budget for hypothesis generation
    adjusted["hypothesis"] *= (1 + 0.4 * cim.risk_appetite)

    # High interpretability → more budget for synthesis
    adjusted["synthesis"] *= (1 + 0.3 * cim.interpretability_priority)

    # Normalize
    total = sum(adjusted.values())
    return {k: v / total for k, v in adjusted.items()}
```

### 5.4 Intent Drift Detection

Over the course of a long research run, the collaborator's intent may change (e.g., as preliminary results come in, they may shift from "exploratory" to "rigor-focused"). The CIM tracks an `update_history` and flags significant intent drift (> 0.3 change in any dimension) for explicit confirmation at the next SmartPause point.

## 6. Epistemic Verification: Design and Implementation

### 6.1 Design Philosophy

The epistemic verification stack is designed around three principles:

1. **Zero trust:** No agent output is accepted as true without independent verification. Plausibility is not evidence.
2. **Diversity of verification:** Different verification mechanisms catch different failure modes. No single mechanism is sufficient.
3. **Traceable provenance:** Every claim in the output has a documented verification path that can be audited.

### 6.2 Gate 1: Literature Gate

**Purpose:** Verify that generated claims are consistent with the established literature.

**Implementation:**

```python
class LiteratureGate:
    def __init__(self, retriever, judge_llm):
        self.retriever = retriever   # Dense retrieval over indexed arXiv/OpenAlex
        self.judge = judge_llm       # LLM judge (different from author LLM)

    def verify(self, claim: str, domain: str) -> GateResult:
        # 1. Retrieve top-K most relevant papers
        papers = self.retriever.search(claim, domain=domain, top_k=10)

        # 2. Check for explicit contradictions
        contradictions = []
        for paper in papers:
            verdict = self.judge.compare(claim, paper.abstract)
            if verdict == "CONTRADICTS":
                contradictions.append(paper)

        # 3. Check for supported-by relationships
        supports = [p for p in papers if self.judge.compare(claim, p.abstract) == "SUPPORTS"]

        return GateResult(
            passed=len(contradictions) == 0,
            contradictions=contradictions,
            supporting_evidence=supports,
            confidence=self._compute_confidence(contradictions, supports)
        )
```

**Failure handling:**
- If contradictions are found, the claim is flagged with the contradicting papers.
- The Author Agent must explicitly address each contradiction: either (a) demonstrate why the contradiction does not apply (with evidence), or (b) revise the claim.
- If the Author Agent cannot address a contradiction, the claim is **blocked from the final output**.

**Important limitations:**
- The literature gate cannot verify claims that are genuinely novel (no prior work supports or contradicts them). For such claims, the gate returns a "NOVEL — unverifiable by literature" status, which increases the requirement for code gate and formal gate verification.
- The gate is only as good as its retrieval coverage. Papers not indexed in arXiv/OpenAlex will not be surfaced.

### 6.3 Gate 2: Code Gate

**Purpose:** Verify that numerical results cited in the manuscript correspond to actual execution log entries.

**Implementation:**

This gate is **fully deterministic** — it does not use an LLM. It parses execution logs and matches numerical values against the manuscript.

```python
class CodeGate:
    def __init__(self, execution_log_db):
        self.log_db = execution_log_db  # Structured store of all execution outputs

    def verify_numerical_claim(self, claim: NumericalClaim) -> GateResult:
        """
        NumericalClaim: {
            "metric_name": "accuracy",
            "value": 0.847,
            "tolerance": 0.001,
            "experiment_id": "exp_branch_a2_run3"
        }
        """
        # Look up the experiment log
        log_entry = self.log_db.get(claim.experiment_id, claim.metric_name)

        if log_entry is None:
            return GateResult(passed=False, reason="No log entry found for this experiment")

        # Check within tolerance
        if abs(log_entry.value - claim.value) > claim.tolerance:
            return GateResult(
                passed=False,
                reason=f"Log shows {log_entry.value}, manuscript claims {claim.value}"
            )

        return GateResult(passed=True, log_reference=log_entry.id)

    def verify_manuscript(self, manuscript: Manuscript) -> list[GateResult]:
        # Extract all numerical claims from the manuscript
        claims = self._extract_numerical_claims(manuscript)
        return [self.verify_numerical_claim(c) for c in claims]
```

**What the Code Gate catches:**
- Values that were copy-pasted incorrectly from logs
- Results from a different experiment run than stated
- Rounded values that exceed the claimed precision
- Hallucinated numbers with no corresponding log entry

**What the Code Gate does NOT catch:**
- Methodological flaws in the experiment itself (addressed by the Reviewer Council)
- Correctly transcribed but incorrectly interpreted results

### 6.4 Gate 3: Formal Gate (Selective)

**Purpose:** For papers with mathematical or algorithmic contributions, verify core claims using a formal verification system.

**Scope:** Applied only when the paper's domain flag includes `MATHEMATICAL_THEOREM`, `ALGORITHM_CORRECTNESS`, or `FORMAL_PROOF`. For empirical ML papers, this gate is skipped.

**Implementation approach (MVP):**

At MVP scale, the formal gate uses **Z3** for first-order logic and arithmetic claims:

```python
class FormalGate:
    def __init__(self):
        self.solver = z3.Solver()

    def verify_arithmetic_claim(self, claim: ArithmeticClaim) -> GateResult:
        """
        Example: verify that a proposed algorithm's time complexity bound holds
        for stated input size constraints.
        """
        # Translate claim into Z3 assertions
        z3_formula = self._translate_to_z3(claim)

        # Attempt to prove by refutation
        self.solver.add(z3.Not(z3_formula))
        result = self.solver.check()

        if result == z3.unsat:
            # Formula is unsatisfiably-negatable = claim is valid
            return GateResult(passed=True, proof_witness=str(self.solver.model()))
        elif result == z3.sat:
            # Counterexample exists
            return GateResult(passed=False, counterexample=str(self.solver.model()))
        else:
            return GateResult(passed=None, reason="Z3 timed out or returned unknown")
```

**Post-MVP upgrade:** Integration with Lean 4 for full theorem proving. `[to verify: feasibility of LLM-to-Lean translation for AI-generated mathematical claims]`

### 6.5 Claim Provenance Graph

Every claim in the final manuscript is linked to its verification path in a **Provenance Graph**:

```
Claim: "Model A achieves 84.7% accuracy on benchmark B"
    ├── Literature Gate: PASSED (3 supporting papers, 0 contradictions)
    │   ├── Paper: doi:10.xxxx/xxxx (supports baseline comparison)
    │   ├── Paper: doi:10.xxxx/xxxx (establishes benchmark standard)
    │   └── Paper: doi:10.xxxx/xxxx (prior SOTA for comparison)
    ├── Code Gate: PASSED
    │   └── Log entry: exp_branch_a2_run3 → accuracy=0.8471, tolerance=0.001
    └── Formal Gate: NOT APPLICABLE (empirical claim)
```

The provenance graph is:
- Attached to the manuscript as a machine-readable appendix
- Retained in the audit log for 90 days
- Used by the ToM Council to assess verification depth during review

## 7. Integration Points with the HRDE Core

### 7.1 ToM Council ↔ Discovery Forest

The ToM Council is invoked at the end of each branch's synthesis phase. Its feedback can trigger:
- **Branch revision:** Specific manuscript sections are revised based on reviewer feedback
- **Branch pruning:** If the council's minimum score falls below the pruning floor after 3 rounds, the branch is pruned
- **Objective insertion:** Reviewer feedback may reveal a missing experiment → new objective inserted into the DOG for that branch

### 7.2 Epistemic Stack ↔ Coder Agent

The Code Gate is invoked after every code execution:
- Execution log is parsed immediately after each run
- Numerical outputs are registered in the log database with experiment ID
- Discrepancies trigger immediate notification to the Coder Agent for investigation

### 7.3 CIM ↔ Hyper-Kernel

The Collaborator Intent Model influences the Hyper-Kernel's optimization targets:
- High rigor → Hyper-Kernel prioritizes modifications that improve verification pass rates
- High speed → Hyper-Kernel prioritizes modifications that reduce wall-clock time per objective
- High novelty → Hyper-Kernel relaxes pruning thresholds to allow more experimental branches to survive

### 7.4 Belief State Tracker ↔ Writer Agent

The Writer Agent receives the Belief State Tracker's output as part of its context:
- Identified reviewer concerns are surfaced as "addresses-required" items in the writing checklist
- The tracker's confidence estimates influence the manuscript's framing (e.g., high reviewer prior for alternative theory → manuscript explicitly addresses the alternative in related work)

## 8. Failure Modes and Mitigations

### 8.1 Echo Chamber (Homogeneous Reviewer Failure)

**Risk:** All 5 reviewer personas share the same base model and therefore share systematic biases, approving content that a truly diverse set of reviewers would reject.

**Mitigation (MVP):** Structurally distinct few-shot examples for each persona, drawn from real reviewer comments in different academic communities. Personas are explicitly instructed to disagree with each other on at least one dimension.

**Mitigation (post-MVP):** Use architecturally diverse base models for different personas (e.g., transformer + SSM + symbolic).

### 8.2 ToM Manipulation (Persuasion Without Truth)

**Risk:** The Intent Alignment Planner or Interpretability Diplomat optimizes for reviewer acceptance by removing, suppressing, or reframing negative findings.

**Mitigation:** Hard constraint: the Interpretability Diplomat may only modify *presentation*, not *content*. Any modification to the verified content layer triggers an audit flag and requires Hyper-Kernel + human review. The Epistemic Verification Stack is invoked *after* any manuscript modification to detect content changes.

### 8.3 Literature Gate Coverage Gaps

**Risk:** The gate misses a key paper that contradicts the main claim because the paper is behind a paywall, not indexed in arXiv/OpenAlex, or written in a non-English language.

**Mitigation:** Run multiple retrieval systems (arXiv, OpenAlex, Semantic Scholar, Google Scholar API if available). Flag coverage limitations in the claim provenance graph. The Limitations section of every manuscript must acknowledge potential uncovered literature.

### 8.4 Code Gate Brittleness

**Risk:** Log format changes or non-deterministic outputs cause false positives (legitimate results flagged as invalid).

**Mitigation:** Configurable tolerance per metric type. Log format is versioned and backward-compatible. Non-deterministic metrics (e.g., training loss with random seed) use range-based rather than point-based matching.

### 8.5 Intent Misalignment Accumulation

**Risk:** CIM drifts in the wrong direction over a long run, gradually misrepresenting the collaborator's actual intent.

**Mitigation:** Intent drift detection (Section 5.4). SmartPause points at configurable intervals that surface current CIM state for human confirmation. The CIM update history is visible in the dashboard.

### 8.6 Adversarial Dialogue Gaming

**Risk:** The Author Agent learns to produce rebuttals that satisfy the reviewer personas without actually addressing the underlying scientific concerns.

**Mitigation:** Rebuttal constraints (Section 4.4). Evidence-grounded rebuttals only. The Epistemic Stack verifies all claims in rebuttals, not just the manuscript. Reviewer personas are updated periodically to prevent the Author Agent from over-fitting to their patterns.

## 9. Implementation Notes and MVP Scope

### 9.1 MVP Scope for ToM Layer

**In scope (Days 31–60 per main roadmap):**
- All 5 reviewer personas with distinct system prompts and rubrics
- 3-round adversarial dialogue protocol
- Basic Belief State Tracker (persona-level; not individual human models)
- Collaborator Intent Model: 4 dimensions (risk appetite, rigor/speed, venue target, collaboration style)
- Intent Alignment Planner: compute budget adjustments only

**Deferred post-MVP:**
- Architecturally diverse base models for reviewer personas
- 3rd-order ToM (modeling what reviewers believe the community expects)
- Multi-collaborator intent modeling
- Real-time persona adaptation from reviewer feedback patterns

### 9.2 MVP Scope for Epistemic Stack

**In scope (Days 31–60):**
- Literature Gate with semantic retrieval (arXiv + OpenAlex)
- Code Gate with deterministic log parsing
- Claim provenance graph (basic)
- DOI anchoring for all citations

**Deferred post-MVP:**
- Formal Gate (Z3 integration)
- Full Lean 4 integration
- Architectural diversity in Literature Gate (secondary verifier)
